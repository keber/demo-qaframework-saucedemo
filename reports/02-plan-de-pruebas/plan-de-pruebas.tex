\section{Objetivo y alcance}
Verificar que login, catálogo, carrito, checkout y navegación de Swag Labs cumplen las reglas de negocio especificadas en la etapa 2, para los 6 usuarios de prueba publicados por el sitio, mediante pruebas E2E automatizadas con Playwright.

\textbf{En alcance}
\begin{itemize}
  \item Autenticación: validaciones del formulario, usuario bloqueado, rutas protegidas, cookie de sesión, logout y expiración (24 TC).
  \item Catálogo: listado, ordenamiento, agregar y quitar, detalle, producto inexistente, comportamiento por usuario y Dynamic Catalog (41 TC).
  \item Carrito: badge, contenido, quitar, persistencia, aislamiento entre usuarios y acceso (19 TC).
  \item Checkout: validaciones del paso 1, resumen y totales con impuesto del 8 \%, confirmación, comprobante PDF y control del flujo (26 TC).
  \item Navegación: menú lateral, Reset App State, encabezado y footer (16 TC).
\end{itemize}

\textbf{Fuera de alcance}
\begin{itemize}
  \item Integración con Azure DevOps (Test Plans, Test Suites, Bugs).
  \item Pruebas de carga (k6) y pruebas de API: la aplicación no expone API propia.
  \item Navegadores distintos de Chromium.
  \item Hallazgos sin regla de negocio (p. ej. longitud máxima del usuario, cookie forjada con \texttt{standard\_user}): se registran como REC, no como TC.
\end{itemize}

\section{Estrategia de prueba}
\begin{itemize}
  \item \textbf{Nivel:} pruebas E2E de interfaz sobre la aplicación desplegada; sin pruebas unitarias ni de API (no hay backend propio).
  \item \textbf{Técnicas:} partición de equivalencia (credenciales y campos obligatorios), transición de estados (carrito, sesión, pasos del checkout), pruebas por usuario contra las mismas reglas y regresión de vistas adyacentes.
  \item \textbf{Orden:} suite SMOKE (P0) primero; si falla un P0 de login o catálogo se detiene el módulo; luego P1, P2 y P3.
  \item \textbf{Aislamiento:} contexto de navegador nuevo por test, sin dependencias de orden entre TC.
  \item \textbf{Polaridad:} cada test asserta lo que exige la regla, no lo que hace la aplicación. Las desviaciones se documentan con \texttt{test.fail()} + archivo DEF; los hallazgos sin regla violada, como REC.
  \item \textbf{Clasificación:} «Automatizado» si es determinista y observable desde el navegador; «Ambos» si una parte requiere inspección humana; «Manual» si no es automatizable (ningún TC del sprint).
\end{itemize}
